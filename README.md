# Project: Flight-Tracker
### Video Demo:  https://youtu.be/pVN3CISTFrE

### Description:
The Flight-Tracker web app was created primarily to alert the user when airline flights become available for a selected route and date.  The app utilizes several features to help search and track flight routes.  Please note: this app is being hosted locally and is not currently available for public use.

#### Key features include:
- Home page allowing the user to search a one way route.
- Secondary page allowing the user to save a route for one click searching in the future
- Option for user to add their email to the tracker which will activate a daily search of that route and send them the results in a formatted email.
  - This part is particularly useful when you want to know as soon as flights become available since there are usually a limited number of seats available via saver fares using points.

### Directions for use:
- On the Flight Tracker page (home page, index.html): Search a one-way flight route by entering the details of the desired route and hit the "Search Flights" button.  The "From", "To", "Departure Date", and "Number of Adults" fields are mandatory.  Optionally you can add the airline code of a specific airline and the max number of route results you would like returned.  Note: the "Airline Code" field must contain only the two digit code for the selected airline.  Only one airline may be searched at a time.  Incorrect entries will simply reload the search page.
  - The search queries the Global Distribution System (GDS) provider Amadeus via an API call and returns available flights listed in order of price.  Each listing will first display a search number and the main itinerary.  Below it, each leg of the itinerary will be listed as "Leg: 1", "Leg: 2", etc.  (please note: the app is using the test environment version of the API as the "move to production workflow" to get a production API key is currently down.  I will move to the production as soon as it becomes available).
  - To set up a route for tracking hit the "To Auto Track Page" button.

- On the Auto Tracker page (autotrack.html):  You are able to store criteria for a future search by entering the desired route details and hitting the "Track Route" button.  Entries are displayed on the below table.  To run a search on any route just hit the "Search Now" button and results will be returned on the home page.  Additionally, you have the option to enter your email address which will appear in the table.  The app is set up to send a daily email with fresh flight search results for each row that contains an email.  An email can be added or removed from an existing tracked route with the corresponding buttons.  Also, a route can be deleted with the "Delete Route" button.
  - The auto email was set up using a Google Cloud gmail API.  I decided to go the proper route which entailed full OAuth authentication.  This took me a bit deeper than I was expecting and I leaned on AI heavily to write the token requesting and handling function.  Although, the Google documentation was pretty good and I did learn a lot.

### Files and other things I implemented/learned:
- app.py - The main file, as you might imagine.  The main workflows include routes to display the homepage with flight search and the auto tracker page.  I guess I'll just go down the list and explain what I learned.
  - Working with APIs.  They were actually more involved than I was expecting.  No one is going to give you any information without an API key code.  At first I was unclear on the difference between making a traditional API call by passing info into HTTP request and other ways such as using a provided software developer kit (SDK).  Like with many things I eventually learned, there are multiple ways to do things and sometimes there is not one clear right way.  Luckily the Amadeus developer site provided a SDK which handled all the OAuth token stuff for me.  Each API system is a little bit different and it took some time to learn the Amadeus one.  I found that there was example API code on the Amadeus which listed the fields you could enter for your query.  However, that was misleading because the entire list of fields you could search on was actually stashed on Github on the OpenAPI Generator section, buried in some YAML file.
  - Storing your API keys and secrets as environmental variables in a .env folder (that you don't commit to GitHub!).  Only reference them via that file in your code via os.getenv.
  - It was fun to see the giant JSON files you would get back from the flight search calls.  I had a great time flexing my non-skills of indexing into lists of dictionaries.  However, I was able to successfully extract and reformat the information I wanted, processing all the flight data in one large function.  This involved iterating through lists of itinerary legs and piecing them all back together in a slightly more readable dictionary before rendering in a table on the HTML file.  I learned how to reformat date formats from iso with .strftime.  
  - Working with an Sqlite3 database is a bit more tedious when not working in the codespace.  There is a cursor involved and I had some help from AI in writing the function that finds and accesses the database.  Also, there were considerations to prevent multiple threads from using the database at the same time, maybe similar to race conditions.  More on this later but I set up my own home server for this site on a Raspberry Pi.  You can't track your database because if you git pull your repository onto your server, the committed database will come with it and overwrite your server data.  Allowing the code to find the path to and access different databases on different systems was tricky.
  - I set up a bunch of routes for storing flights in the database, adding and deleting emails.  That was all fairly straightforward as described in class.
  - The gmail API and Google Cloud service was a lot to take in.  There is so much content and functionality available through the Google Cloud service.  All I wanted to do was send an email.  Between the Google quickstart guide and some tutorials on Medium, Geeks for Geeks, and some others I was able to make it work.  The most frustrating part was dealing with the OAuth token and secret because I was using the API in test mode which required you to click through a consent screen to make sure you trust the person/app trying to access your email.  You can't click through a browser window on a headless server so I had to set my Google Cloud project to "in production" to get a non expiring refresh token and then copy it over to the server.
- index.html, autotrack.html - The home page, which is actually less useful than the secondary flight tracker page (autotrack.html).  Thanks to what I learned in class it was pretty easy to set up getting the info from the user input fields and getting the results back onto the page.  Bootstrap made it so I was able to use almost no CSS.  I asked ChatGPT for some style suggestions and it was fun to add the bootstrap class information one by one and hit refresh to see what effect the code had as the page slowly went from a 90's GeoCities site to a modern, mobile friendly version.  I had ChatGPT generate some corny header images for me.  You could sink a lot of time into messing around with the aesthetics and bootstrap stuff but I decided to cut it where it is now.
- email_template.html - I learned how to pass HTML into an email body, which involved using render_template just like you would a web page route.  Now instead of a migraine inducing JSON list you get a nice clean table in your inbox.
- tracked.db - The main database which is not on GitHub because I don't want to overwrite my server database.  This took a little time to wrap my brain around because I had to understand (I still don't fully understand) how to configure the database getting function to look in two different places, one for when running on my dev computer and a different one on the server.  Now I have the server database tucked away safely in whatever Linux folder is conventional to store your app data in.  I wrote it down somewhere.  I caught a bug where I was allowing people (myself) to enter blank data into the database and that would break my datetime reformatting function.  I fixed that one.
- daily_search.sh and run_daily_search.py -These were created to automatically run a function in app.py to check the database for emails present, run a search, and send it to the email every day.  I used cron to schedule the job.  Again, it was tricky to configure it to work and test it on my dev computer then switching the code up for pushing it onto the server.  I'm seeing a theme here.
- flight-offers.json - Contains the data you get back when making a flight search call.  Just in case anyone wants to look at it.
- quickstart.py - Was used to get the gmail API working.  I really shouldn't have it in there but I think superstition is making me keep it in case it's needed for something.
- Setting up the Raspberry Pi home server was one of the most demanding parts of the project.  You have to manage everything in the terminal, you don't have a (good) code editor to edit things, you just have to pull from GitHub and hope that you set up your code correctly to account for the different folder structure (maybe I should get Docker).  You can't commit any API keys, secrets, or tokens, so you have to add all that manually.  So much fun happened.  Configuring ufw firewall to let certain ports though.  I used Gunicorn and then Caddy as a reverse proxy web server (imagine how much I would be complaining if I used Nginx) so I needed to learn what a Caddyfile is and where to put it.  Also, I downloaded the Caddy install file as a binary from the website so I had to figure out how to make it into an executable file.  Changing ownership of files in Linux.  Setting up systemctl processes to automatically start Caddy and the flight-tracker app on startup.  Managing environmental variables and paths.  Setting up a hostname.  Setting up journals and logs to catch error data.  Understanding the process of deploying updates to the server - pip freeze > requirements.txt, commit, pull on server, go into virtual environment, install requirements.txt, restart app, cross fingers . . .

### Final notes:
Overall, this project (as well as the entire class) was incredibly fun and engaging.  The class set me up well to be able to swim through the waters of software development documentation and direct my own learning path for the future.  I still can't find where my previous orders live on the Uber Eats app but at least I know how it works behind the scenes.  During the project build almost every new feature you want to implement requires a mini class of its own.  I constantly found myself balancing the want to do an exhaustive deep dive into the subject vs learning the minimal amount to get the job done.  If I spent two weeks or more each to fully learn everything (git, web server setup, Bootstrap, CSS, JavaScript, Google Cloud API, Linux system commands and folder structure, authentication, environmental variables, etc.) this project wouldn't be done for a few more months.  

AI was instrumental in my learning process.  I don't know if it was for the better or for the worse.  I treated AI as a teacher instead of a do-er.  As with the codespace duck, I gave ChatGPT some preliminary ground rules, that I was doing a class project and I would like to err on the side of more explanation and context rather than just spitting out the answer.  Any time you hit a road block you can just ask ChatGPT about it and get a direct line to the exact information you need, explained for your specific software situation and context.  It was such a shortcut to allow for accelerated learning and fast progress.  

However, considering how things had to be done prior to this tool being available, you had to just do a web search on the subject, which usually works fine for explaining what a certain file type is or what some acronym means.  If you have a more complicated problem though, you either have to wade through message board forums, hoping that someone has solved a similar problem, or (and this might be where AI is selling me short) you need to start from the begining on each subject so that you fully understand it from the ground up and you can diagnose the problem with your own innate understanding of how it works.  This sounds like a more complete learning experience, albeit a more lengthy and harder path to the final product.  I guess either way you go, you can't get around the relationship of the more time you devote to learning something, the more completely you understand it.
